# Еженедельные публикации через `/announce`

## Что делает система

Команда `/announce` доступна только администраторам из `ADMIN_IDS` и открывает два режима:

1. **Отправить сейчас** — существующая массовая рассылка запускается сразу после подтверждения.
2. **Отложенная доставка** — сообщение сохраняется и автоматически отправляется в выбранный день каждую неделю.

Для расписания доступны все семь дней:

- понедельник;
- вторник;
- среда;
- четверг;
- пятница;
- суббота;
- воскресенье.

Время всегда трактуется в часовом поясе `Europe/Moscow`. Расписание повторяется еженедельно и действует, пока администратор не изменит или не удалит его.

На каждый день недели можно сохранить одну публикацию. Новая настройка существующего дня заменяет его прежнее время, сообщение и аудиторию.

## Как отправить публикацию сразу

1. Откройте личный диалог с ботом от имени администратора.
2. Отправьте команду `/announce`.
3. Нажмите **Отправить сейчас**.
4. Отправьте боту публикацию, которую нужно разослать.
5. Выберите аудиторию:
   - **Все** — все пользователи из таблицы `users`;
   - **Оплатили** — пользователи со статусом `paid`;
   - **Застряли в регионе** — пользователи со статусом `rfool`;
   - **Не платили и не застряли** — пользователи без статуса `paid` или `rfool`.
6. Бот пришлёт копию публикации для проверки и покажет выбранную аудиторию.
7. Нажмите **Да**, чтобы начать рассылку, или **Нет**, чтобы отменить её.
8. После завершения бот покажет общее число получателей, количество успешных отправок и ошибок.

## Как создать еженедельную публикацию

1. Отправьте команду `/announce`.
2. Нажмите **Отложенная доставка**.
3. Выберите нужный день недели.
4. Если день ещё не настроен, бот сразу попросит время. Если запись уже существует, сначала нажмите **Изменить**.
5. Отправьте время отдельным текстовым сообщением строго в формате `ЧЧ:ММ`:
   - `09:00` — корректно;
   - `18:45` — корректно;
   - `9:00` — некорректно, нужен ведущий ноль;
   - `24:00` — некорректно;
   - `12:60` — некорректно.
6. Отправьте саму публикацию.
7. Выберите аудиторию.
8. Проверьте созданное ботом превью, день, время, часовой пояс и аудиторию.
9. Нажмите **Да**. Только после подтверждения запись попадёт в PostgreSQL и активный планировщик.

Пример: если выбрать субботу и указать `11:30`, публикация будет отправляться каждую субботу в 11:30 по Москве.

## Как посмотреть текущее расписание

1. Отправьте `/announce`.
2. Нажмите **Отложенная доставка**.
3. В меню возле настроенных дней будет показано время, например:

   ```text
   Понедельник — 10:00
   Вторник
   Среда — 17:30
   Четверг
   Пятница
   Суббота — 11:30
   Воскресенье
   ```

День без времени ещё не настроен. После нажатия на настроенный день бот также покажет выбранную аудиторию.

## Как изменить запись

1. Откройте `/announce` → **Отложенная доставка**.
2. Нажмите день, рядом с которым уже указано время.
3. Нажмите **Изменить**.
4. Заново укажите время, публикацию и аудиторию.
5. Проверьте превью и подтвердите изменение.

Изменение полностью заменяет прежнюю запись этого дня. Старая публикация больше отправляться не будет.

## Как удалить запись

1. Откройте `/announce` → **Отложенная доставка**.
2. Нажмите настроенный день.
3. Нажмите **Удалить**.
4. Бот сразу удалит запись из PostgreSQL и активного планировщика.

Дополнительное подтверждение удаления не запрашивается. После удаления день останется в меню, но время рядом с ним исчезнет.

## Какие сообщения можно планировать

Рассылка использует Telegram `copyMessage`, как и прежний режим немедленной отправки. За счёт этого сохраняются поддерживаемые Telegram содержимое и оформление исходного сообщения, включая текст, форматирование, фото, видео, документ и подпись к медиа.

Публикация хранится как ссылка на исходное сообщение: ID чата администратора и ID сообщения. Поэтому исходное сообщение в диалоге с ботом нельзя удалять, пока соответствующая запись расписания активна. Если Telegram больше не сможет получить исходное сообщение, запланированная отправка завершится ошибками копирования.

Медиагруппа (альбом из нескольких сообщений) не объединяется автоматически в одну публикацию: каждое сообщение Telegram имеет собственный ID. Текущий сценарий рассчитан на одно Telegram-сообщение на один день.

## Хранение и восстановление после перезапуска

Настройки находятся в таблице PostgreSQL `scheduled_announcements`. В ней хранятся:

- номер дня недели от `0` до `6`;
- московское время отправки;
- аудитория;
- ID исходного чата и сообщения;
- ID администратора, создавшего запись;
- дата последней отправки;
- количество успешных и неуспешных отправок в последний запуск.

При каждом старте бот читает активные записи из PostgreSQL и заново создаёт задания APScheduler. Перезапуск процесса не удаляет расписание.

Если бот был полностью выключен в момент отправки, пропущенная за время простоя публикация задним числом не рассылается. После запуска будет ожидаться следующее недельное срабатывание. Пятиминутный `misfire_grace_time` помогает только при короткой задержке работающего процесса или event loop.

## Первый запуск и обновление базы данных

Для новой базы таблица уже включена в `db/init/001_bot_schema.sql`.

Для существующей базы бот при запуске выполняет идемпотентный `CREATE TABLE IF NOT EXISTS`. Он также заменяет прежнее ограничение `0..4` на `0..6`, чтобы база принимала субботу и воскресенье. Отдельно запускать SQL-миграцию не нужно.

Пользователь PostgreSQL из переменных `DB_USER`, `DB_PASSWORD`, `DB_NAME` и `DB_HOST` должен иметь права `CREATE` и `ALTER` в рабочей схеме. В стандартном развёртывании из `deploy/README.md` пользователь `bot` является владельцем базы и уже имеет необходимые права.

## Развёртывание обновления на сервере

Ниже предполагается стандартный путь `/opt/appstore_bot` и systemd-сервис `appstore-bot.service`.

1. Сделайте резервную копию базы перед обновлением:

   ```bash
   sudo docker exec appstore-bot-db pg_dump -U bot -d appstore_bot \
     > /opt/appstore_bot/appstore_bot_before_announcements.sql
   ```

2. Получите новую версию проекта выбранным способом. При использовании Git:

   ```bash
   cd /opt/appstore_bot
   sudo -u appstorebot git pull --ff-only
   ```

3. Обновите зависимости. Новых пакетов функция не требует, но эта команда синхронизирует окружение с `requirements.txt`:

   ```bash
   cd /opt/appstore_bot
   sudo -u appstorebot .venv/bin/pip install -r requirements.txt
   ```

4. Выполните статическую проверку Python-файлов:

   ```bash
   cd /opt/appstore_bot
   sudo -u appstorebot .venv/bin/python -m compileall -q commands repository services main.py
   ```

5. Запустите unit-тесты:

   ```bash
   cd /opt/appstore_bot
   sudo -u appstorebot .venv/bin/python -m unittest discover -s tests -v
   ```

   Ожидаемый итог: `Ran 3 tests` и `OK`.

6. Перезапустите бота:

   ```bash
   sudo systemctl restart appstore-bot.service
   sudo systemctl status appstore-bot.service --no-pager
   ```

7. Проверьте журнал запуска:

   ```bash
   sudo journalctl -u appstore-bot.service -n 100 --no-pager
   ```

   В журнале должны присутствовать сообщения о проверенной схеме базы и запущенном планировщике. Не должно быть ошибок `permission denied`, `scheduled_announcements` или `Scheduler error`.

8. Проведите ручную проверку:
   - откройте `/announce`;
   - убедитесь, что видны суббота и воскресенье;
   - создайте тестовую запись на ближайшее время;
   - проверьте превью;
   - дождитесь рассылки;
   - удалите тестовую запись через меню.

## Проверка данных непосредственно в PostgreSQL

Посмотреть всё расписание:

```bash
sudo docker exec -it appstore-bot-db psql -U bot -d appstore_bot -c \
  "SELECT weekday, send_time, audience, source_chat_id, source_message_id, last_sent_at, last_success, last_failed FROM scheduled_announcements ORDER BY weekday;"
```

Соответствие значений дня недели:

| `weekday` | День |
|---:|---|
| 0 | Понедельник |
| 1 | Вторник |
| 2 | Среда |
| 3 | Четверг |
| 4 | Пятница |
| 5 | Суббота |
| 6 | Воскресенье |

Проверить ограничение таблицы:

```bash
sudo docker exec -it appstore-bot-db psql -U bot -d appstore_bot -c \
  "SELECT conname, pg_get_constraintdef(oid) FROM pg_constraint WHERE conrelid = 'scheduled_announcements'::regclass;"
```

Для `scheduled_announcements_weekday_check` должен отображаться диапазон от `0` до `6`.

## Режим `TEST_MODE`

Если `TEST_MODE=True`, и немедленная, и запланированная рассылка отправляются только пользователям из `ADMIN_IDS`. Выбранная аудитория всё равно сохраняется, но до отключения тестового режима реальные пользователи сообщения не получают.

После переключения `TEST_MODE` нужен перезапуск процесса, поскольку конфигурация читается при старте.

## Диагностика проблем

### Суббота или воскресенье не отображаются

- Убедитесь, что на сервер попал новый `commands/announce.py`.
- Перезапустите systemd-сервис.
- Отправьте новую команду `/announce`: старое сообщение с inline-кнопками само не обновится.

### Бот падает при запуске с ошибкой прав PostgreSQL

Пользователю базы не хватает права создать таблицу или изменить ограничение. Проверьте владельца базы и таблицы. В стандартной схеме владельцем должен быть пользователь `bot`.

### Запись есть, но сообщение не отправилось

- Проверьте, что бот работал в назначенное время.
- Проверьте часовой пояс: используется Москва, а не локальное время устройства администратора.
- Проверьте, что исходное сообщение не удалено.
- Проверьте `TEST_MODE`: в тестовом режиме получателями будут только `ADMIN_IDS`.
- Посмотрите `last_sent_at`, `last_success` и `last_failed` SQL-запросом выше.
- Просмотрите журнал: `sudo journalctl -u appstore-bot.service -n 200 --no-pager`.

### Время уже прошло, но публикация не отправляется

Для еженедельного расписания после сохранения прошедшего времени выбирается следующее наступление этого дня. Например, если в субботу в 15:00 сохранить субботу на 10:00, первая отправка будет в следующую субботу в 10:00.

### Нужно несколько публикаций в один день

Текущая модель намеренно ограничена одной записью на день. Чтобы поддержать несколько публикаций, потребуется заменить уникальность по `weekday` на отдельный ID расписания и добавить выбор конкретной записи для изменения и удаления.
